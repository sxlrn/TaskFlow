АНОТАЦІЯ
Дана курсова робота присвячена проєктуванню, програмній реалізації та оптимізації сучасної клієнт-серверної системи управління проєктами та задачами «TaskFlow» для організацій. Досліджено та побудовано архітектуру системи на базі професійного стеку: React, TypeScript, React Query та TailwindCSS для клієнтського боку, а також Node.js та Express для серверної логіки. Взаємодія з базою даних MySQL здійснюється через сучасної ORM інструмент Prisma, що забезпечує строгу типізацію та захист від невідповідності типів на рівні БД. Проведено ретельне дослідження та реалізацію сучасних стандартів веб-безпеки, таких як автентифікація JWT (з ротацією access/refresh токенів у HttpOnly cookie), багаторівневий контроль доступу на основі ролей (RBAC admin, manager, worker), логування спроб авторизації (AuthLog), Rate limiting для запобігання DDoS-атакам, а також впровадження Zod-валідації вхідних даних.
ABSTRACT
This coursework report is devoted to the architectural design, implementation, and security auditing of a modern client-server project and task management web-oriented platform "TaskFlow" customized for corporate use. The technology stack consists of React, TypeScript, React Query, and TailwindCSS for the client application, and Node.js with Express for the API server. Database layer operates via MySQL server coupled with modern Prisma ORM. Significant emphasis has been placed on establishing modern security protocols: robust JWT authentication (with access/refresh token rotation stored in secure HttpOnly cookies), Role-Based Access Control (RBAC admin, manager, worker), Rate Limiting, secure logging of all auth requests via AuthLog model, and strict schema validation with Zod library.

Актуальність теми. У сучасних умовах цифровізації бізнесу та активного впровадження хмарних рішень в організаційну структуру підприємств особливого значення набуває побудова інтегрованих систем автоматизації спільної діяльності. Робота сучасних команд проходить у надзвичайно динамічному темпі, де кожен працівник може виконувати паралельно кілька складних завдань, а менеджери проєктів змушені в реальному часі координувати пріоритети, дедлайни та завантаженість персоналу. Застосування пласких та неструктурованих інструментів комунікації (електронна пошта, корпоративні месенджери) не забезпечує належної прозорості та призводить до втрати важливої інформації, зриву термінів та зниження загальної ефективності праці. У зв'язку з цим, спеціальність 126 (Інформаційні системи та технології) фокусується на проєктуванні та впровадженні високонадійних програмних архітектур, що вирішують ці прикладні бізнес-задачі.
Існуючі великі закриті комерційні платформи (такі як Jira або Trello) часто мають високу вартість ліцензування на кожного користувача, є надто складними у налаштуванні для невеликих та середніх компаній, а головне не надають можливості гнучко кастомізувати внутрішні робочі процеси без значних фінансових вкладень. Більше того, для організацій з високими вимогами до безпеки використання зовнішніх хмарних SaaS-систем несе ризик витоку конфіденційних даних та відсутності повного контролю над журналами авторизації (аудит безпеки входу). Таким чином, розробка та проєктування власної веб-орієнтованої інформаційної системи управління проєктами та задачами «TaskFlow», яка враховує специфіку ролей, забезпечує високі стандарти локальної безпеки та має дружній оптимізований інтерфейс, є вкрай актуальним завданням для індустрії інформаційних систем та технологій.
Сфера застосування розробки ІТ-компанії, проектні офіси комерційних організацій, науково-дослідні інститути та лабораторії, а також навчальні заклади, що потребують локального контролю над хостингом та даними користувачів під час розробки складних систем.
Об’єкт дослідження процеси організації спільної командної роботи, автоматизації життєвого циклу завдань та побудови інформаційних потоків у веб-орієнтованих корпоративних середовищах.
Предмет дослідження архітектура, реляційні моделі даних, алгоритми контролю доступу (RBAC), протоколи автентифікації та оптимізація користувацького інтерфейсу клієнт-серверної системи управління завданнями.
Мета роботи проєктування, розробка та дослідження захищеної інформаційної системи «TaskFlow» з ієрархічною деревоподібною моделлю підзадач, ротацією JWT-токенів у HttpOnly cookies, вбудованим аудитом спроб авторизації та оптимізованою Kanban-дошкою.

Теоретичні відомості
1.1. Клієнт-серверна та багаторівнева (N-tier) архітектура
Сучасне проєктування інформаційних систем базується на розділенні відповідальності між різними компонентами системи для полегшення супроводу, масштабування та тестування. Веб-орієнтована платформа «TaskFlow» спроєктована за класичною багаторівневою (N-tier) клієнт-серверною архітектурою, яка передбачає логічне та фізичне розбиття на три основні шари. Такий архітектурний підхід забезпечує надійність функціонування системи при великих навантаженнях, оскільки кожна підсистема може масштабуватись незалежно.
Рівень представлення (Presentation Layer) реалізовано як Single Page Application (SPA) на базі React.js та TypeScript. Клієнтська частина завантажується в браузер користувача у вигляді скомпільованого статичного пакету і повністю бере на себе відповідальність за рендеринг елементів інтерфейсу, відстеження стану локальних змін та реакцію на дії користувача. React використовує технологію Virtual DOM, що дозволяє мінімізувати пряме звернення до реального DOM браузера. React обчислює різницю між старим та новим станами (процес reconciliation) та оновлює лише ті елементи, які реально змінились, що забезпечує плавний і миттєвий відгук програми без необхідності повного перезавантаження сторінок.
Рівень прикладних служб / бізнес-логіки (Application/Logic Layer) представлений сервером на платформі Node.js із використанням фреймворку Express.js. Він виступає посередником між користувачем та базою даних. Сервер обробляє HTTP-запити від клієнта, проводить авторизаційні перевірки (перевіряє роль користувача, валідність його JWT-токена), викликає відповідні контролери, здійснює валідацію вхідних даних та обчислення бізнес-правил. Node.js використовує подієво-орієнтовану, неблокуючу модель вводу-виводу (Event Loop), що дозволяє обслуговувати тисячі одночасних з'єднань з мінімальними витратами оперативної пам'яті.
Рівень доступу до даних та збереження (Data Layer) складається з реляційної системи керування базами даних MySQL та проміжного шару Prisma ORM. Prisma виступає об’єктно-реляційним картографом (Object-Relational Mapper), що дозволяє розробнику взаємодіяти з базою даних через типізований інтерфейс TypeScript, виключаючи написання небезпечних сирих SQL запитів вручну. Prisma генерує оптимальні SQL запити на основі своєї внутрішньої Rust-орієнтованої структури та забезпечує ефективне керування пулом з'єднань (connection pooling) з базою даних, що критично для високонавантажених систем спеціальності 126.
1.2. Шаблон проєктування MVC (Model-View-Controller)
Шаблон проєктування Model-View-Controller є фундаментальним стандартом побудови інтерфейсів та бізнес-логіки програмних систем. Він розділяє додаток на три взаємопов'язані частини, що значно підвищує рівень модульності коду. У сучасних SPA веб-додатках MVC зазнає певної еволюції. Замість класичного серверного рендерингу, де контролер безпосередньо генерував HTML-код представлення, відбувається чітке розділення: клієнтський бік має свою локальну тріаду MVC, а серверний бекенд фокусується на обробці моделей та контролі бізнес-логіки.
Model (Модель) відповідає за бізнес-дані, правила їх валідації та зв’язки. У нашому проєкті моделі описані в декларативному вигляді у файлі schema.prisma. Вони трансформуються в реальні таблиці бази даних MySQL і типізовані класи в Node.js. Модель повністю ізольована від користувацького інтерфейсу і нічого не знає про те, як дані будуть відображатись.
View (Представлення) відповідає за візуалізацію даних моделі для користувача. У SPA архітектурі представлення повністю винесене на сторону клієнта (React) у вигляді багаторазових UI-компонентів. Вони підписуються на стан (state) та автоматично оновлюються при зміні стейту. Клієнтська частина використовує декларативний стиль опису інтерфейсу, що робить його передбачуваним та простим для налагодження.
Controller (Контролер) обробляє дії користувача (запити до API) та викликає зміни в моделях чи відображеннях. У бекенді контролери реалізовані у вигляді асинхронних функцій Express-маршрутизатора, які отримують дані запиту, здійснюють бізнес-логіку та повертають оновлені дані у вигляді JSON. На стороні клієнта роль контролера виконують обробники подій (event handlers) та кастомні React hooks (наприклад, мутації React Query), які ініціюють відправку HTTP-запитів на сервер.
1.3. Архітектурний стиль REST API
Взаємодія між клієнтом (React) та сервером (Node.js) реалізована за допомогою безстанового (stateless) інтерфейсу REST API. Це означає, що сервер не зберігає стан сесії клієнта в оперативній пам'яті. Кожен запит містить у собі повну інформацію для його ідентифікації та виконання (Bearer Access Token у заголовку HTTP Authorization). REST забезпечує уніфікований інтерфейс взаємодії, де кожен ресурс (задача, проєкт, коментар) має свою унікальну URL-адресу, а операції над ними виконуються за допомогою стандартних дієслів протоколу HTTP (GET для читання, POST для створення, PUT для повного оновлення, DELETE для видалення).
Ми спроєктували REST API відповідно до архітектурних обмежень Роя Філдінга: Клієнт-Сервер, Безстановость, Кешованість, Шаруватість системи та Одноманітність інтерфейсу. Завдяки цьому клієнт та сервер є повністю незалежними. Бекенд може змінити внутрішню реалізацію збереження даних або навіть мову програмування, але якщо структура API ендпоінтів та формат JSON відповідей залишаться незмінними, клієнтський додаток продовжить працювати без жодних переробок. Це значно спрощує подальше розширення системи та її інтеграцію з мобільними застосунками чи сторонніми сервісами.
1.4. JWT автентифікація з ротацією токенів у HttpOnly cookie
Безпека автентифікації користувачів є наріжним каменем сучасних корпоративних систем. Для платформи «TaskFlow» було відкинуто використання стандартних сесій на базі оперативної пам'яті сервера (stateful sessions) та вразливе збереження токенів у клієнтському LocalStorage. Замість цього розроблено надійну схему на базі двох типів токенів (JSON Web Tokens):
1. Access Token короткоживучий JWT-токен (дійсний 15 хвилин), підписаний секретним ключем сервера за алгоритмом HMAC-SHA256. Він містить ID користувача, його email та роль. Відправляється клієнтом у кожному HTTP-запиті в заголовку Authorization (Bearer schema). Сервер верифікує токен миттєво без звернення до бази даних MySQL, що мінімізує завантаження СУБД.
2. Refresh Token довгоживучий токен (дійсний 7 днів), який зберігається у базі даних MySQL і використовується виключно для автоматичної генерації нового access-токена після закінчення його терміну. Щоб унеможливити викрадення refresh-токена через XSS (Cross-Site Scripting) атаки та шкідливі розширення браузера, він записується сервером у HTTP-відповіді як cookie із прапорцями `HttpOnly` (забороняє читання токена через JavaScript), `Secure` (передача тільки по захищеному HTTPS) та `SameSite=Strict/None`.
Для захисту від повторного використання токенів зловмисниками впроваджено механізм ротації refresh-токенів (Refresh Token Rotation). При кожному запиті на оновлення сесії стара пара токенів повністю анулюється, старий refresh-токен видаляється з бази даних, а користувачу повертається абсолютно новий набір. Якщо зловмисник спробує використати раніше перехоплений старий refresh-токен, сервер зафіксує це як порушення безпеки і миттєво анулює всі активні сесії даного користувача, вимагаючи повторного входу. Це гарантує захист корпоративних даних від несанкціонованого доступу.
1.5. Рольовий контроль доступу (RBAC) та Zod валідація
Для розмежування повноважень користувачів реалізовано рольову модель доступу (Role-Based Access Control, RBAC). На рівні Express розроблено middleware, які перевіряють роль, закодовану в розшифрованому Access-токені:
admin: має необмежені права. Може редагувати та видаляти будь-які проєкти, завдання та коментарі, а також керувати користувачами.
manager: може створювати нові проєкти, ставити завдання працівникам, редагувати їх опис та терміни. Обмежений у можливості видалення глобальних системних налаштувань.
worker: виконавець завдань. Може переглядати дошку, змінювати статус виключно тих завдань, де він вказаний виконавцем (assignee_id), а також створювати, редагувати та видаляти тільки свої власні коментарі.
Для захисту бекенду від некоректних або шкідливих даних надійно впроваджено бібліотеку Zod. Перед обробкою запитів контролерами тіла запитів (request bodies) перевіряються через строго типізовані схеми валідації. Це повністю відсікає спроби передати SQL-ін'єкції чи Prototype Pollution атаки на етапі парсингу HTTP-запиту, забезпечуючи стійкість прикладного рівня.

2.1. Проєктування реляційної структури бази даних MySQL
Для надійного збереження даних та забезпечення зв'язків між сутностями було спроєктовано реляційну базу даних у СУБД MySQL. Схема складається з наступних ключових сутностей, спроєктованих відповідно до вимог третьої нормальної форми (3NF):
1. Таблиця User: Зберігає дані користувачів. Містить поля: id (первинний ключ, автоінкремент), email (унікальний рядок), password (хешований пароль), full_name (ім'я та прізвище), role (роль в системі: admin, manager, worker), avatar_color (колір аватара) та department (професійна посада/відділ).
2. Таблиця Project: Описує проєкт, у межах якого створюються задачі. Пов'язана відношенням багато-до-одного з користувачем-менеджером (manager_id -> User.id). Містить назву, опис, пріоритет, колір та термін виконання (deadline).
3. Таблиця Task: Описує безпосередньо завдання. Пов'язана з проєктом (project_id), виконавцем (assignee_id) та автором (reporter_id). Особливістю є поле parent_id (зовнішній ключ, що посилається на Task.id), яке дозволяє будувати необмежену деревоподібну ієрархію підзадач.
4. Таблиця Comment: Зберігає текстові повідомлення в обговоренні кожної задачі. Пов'язана зв'язками один-до-багатьох із таблицями Task та User.
5. Таблиця RefreshToken: Сесії авторизації. Містить унікальний токен, посилання на користувача та час експірації. Необхідна для ротації JWT сесій та блокування вкрадених токенів.
6. Таблиця AuthLog: Журнал аудиту авторизацій. Зберігає час спроби, email, IP-адресу клієнта та прапорець успішності (success).
7. Таблиця _prisma_migrations: Системна таблиця Prisma ORM. Зберігає історію та поточний стан версій структури бази даних для автоматичного контролю міграцій.
Нижче наведено детальну ER-діаграму відношень бази даних. Тут чітко видно зв'язки один-до-багатьох, правила каскадного видалення (Cascade Delete) для пов'язаних сутностей, а також рекурсивне самопосилання для таблиці завдань, що є базою для побудови деревоподібних структур підзадач.

2.2. Розробка прикладного API-сервера на Node.js та Express
Серверна частина системи спроєктована за стандартами побудови RESTful веб-служб на базі Node.js та Express. Весь код написаний на мові TypeScript, що забезпечує контроль відповідності типів на етапі компіляції та виключає виникнення помилок через некоректні формати даних під час виконання. Для взаємодії з клієнтом використовується JSON-формат.
Маршрутизація Express структурована за модульним принципом. Кожен ресурс (auth, projects, tasks, comments, users) має свій окремий файл маршрутів (router), які делегують обробку запитів асинхронним функціям відповідних контролерів. Для гарантування безпеки та валідності вхідних даних кожен маршрут захищено ланцюжком проміжних обробників (middleware):
1. Auth Middleware перевіряє наявність та валідність Access-токена в заголовках запиту, розшифровує його та записує дані авторизованого користувача в об'єкт запиту (req.user).
2. Role Middleware перевіряє роль користувача на відповідність необхідному рівню доступу для даного ендпоінту (наприклад, створювати проєкт може лише admin або manager).
3. Validation Middleware використовує Zod схеми для верифікації структури тіла запиту (req.body) або URL-параметрів (req.params). Якщо дані некоректні, клієнту автоматично повертається відповідь 400 Bad Request із детальним списком помилок.
Для спрощення процесу тестування та інтеграції клієнтської частини бекенд сервіс автоматично генерує та відображає інтерактивну документацію REST API через інструмент Swagger UI за стандартом OpenAPI 3.0. Документація містить повний перелік маршрутів, очікуваних вхідних параметрів та схем відповідей.

3.2. Робота з ієрархічним деревом підзадач
Великі завдання в компанії завжди потребують декомпозиції. В системі «TaskFlow» реалізовано ієрархічну модель: користувач може створити підзадачу для будь-якої задачі, формуючи деревоподібну структуру необмеженої глибини. На головній Kanban-дошці відображаються лише первинні високорівневі задачі (parent_id = null), щоб не захаращувати робочий простір. При натисканні на задачу відкривається модальне вікно деталей завдання, у якому відображається дерево всіх підзадач.
Дерево підзадач рендериться рекурсивно, відображаючи назву підзадачі, виконавця та її поточний статус. Користувач може безпосередньо з цього вікна створювати нові підзадачі, які автоматично прив'язуються до батьківського завдання. Це дозволяє ефективно розподіляти обов'язки та контролювати хід виконання складних робіт.

3.4. Авторизація та реєстрація користувачів
Для забезпечення безпеки, ідентифікації користувачів та розмежування прав доступу в системі «TaskFlow» реалізовано інтерфейси авторизації та реєстрації. Форма реєстрації дозволяє новому співробітнику створити обліковий запис, вказавши унікальний email, пароль, повне ім'я, професійну посаду (департамент) та початкову роль у системі. Всі поля форми проходять строгу клієнтську валідацію в реальному часі за допомогою бібліотеки Zod, що запобігає надсиланню некоректних даних на сервер.
Форма авторизації забезпечує безпечний вхід до робочого простору за допомогою технології JWT (JSON Web Token) з механізмом ротації сесій. Після перевірки логіна та хешованого пароля на сервері, клієнт отримує Access Token (що зберігається в оперативній пам'яті для авторизації API-запитів) та Refresh Token (який безпечно записується у захищені HttpOnly cookie). Це гарантує надійний захист від XSS-атак та дозволяє користувачеві залишатися в системі після перезавантаження сторінки.

4.1. Покрокова інструкція з інсталяції та запуску
Завдяки використанню стандартизованих скриптів розгортання, запуск проєкту на новому локальному комп'ютері здійснюється за кілька хвилин без специфічних навичок системного адміністрування. Нижче наведено покрокову інструкцію:
Крок 1. Перейдіть у директорію backend, встановіть npm залежності за допомогою команди npm install та вкажіть параметри підключення до локальної бази даних MySQL у створеному файлі .env (параметр DATABASE_URL). Також вкажіть секретні ключі для JWT.
Крок 2. Виконайте автоматичне створення таблиць бази даних та генерацію клієнта Prisma за допомогою команд npx prisma db push та npx prisma generate. Це синхронізує модель даних з вашим MySQL сервером.
Крок 3. Запустіть бекенд dev-сервер за допомогою команди npm run dev. Сервер почне прослуховувати запити на порту 5000.
Крок 4. Відкрийте новий термінал, перейдіть в папку frontend, встановіть клієнтські залежності через npm install.
Крок 5. Запустіть клієнтський сервер за допомогою команди npm run dev. Додаток автоматично відкриється у вашому браузері за адресою http://localhost:5173.

1. Ефективність сучасних парадигм розробки. Використання трирівневої (N-tier) архітектури та шаблону MVC забезпечило повне логічне розділення інтерфейсу користувача (React SPA) та прикладного Express-сервера, що спростило супровід та масштабування коду.
2. Надійність та безпека даних. Реалізація автентифікації на базі ротації JWT-токенів у захищених HttpOnly cookie повністю виключила можливість перехоплення сесій через XSS атаки. Вбудоване логування авторизацій (AuthLog) та лімітування частоти запитів (Rate limiting) забезпечили стійкість системи до Brute-force атак.
3. Високі стандарти користувацького досвіду (UX). Оптимізація Kanban-дошки за допомогою CSS Flexbox повністю усунула хронічну проблему подвійного скролбару (double scrollbars), створивши преміальний адаптивний інтерфейс з ізольованим скролінгом колонок.
4. Якість кодової бази. Покриття системи 49 автоматичними тестами (Jest, Vitest) та інтеграція документації OpenAPI/Swagger гарантують високу стабільність платформи та простоту її інтеграції з іншими ІТ-системами організації.

  id              Int        @id @default(autoincrement())

  priority        Priority   @default(medium)

  project         Project    @relation(fields: [project_id], references: [id], onDelete: Cascade)

Додаток Б. Реалізація Контролера Автентифікації (auth.controller.ts)
import { Request, Response } from 'express';
import bcrypt from 'bcryptjs';
import prisma from '../utils/prisma';
import { generateAccessToken, generateRefreshToken } from '../utils/jwt';
export const login = async (req: Request, res: Response): Promise<void> => {
  try {
    const { email, password } = req.body;
    const user = await prisma.user.findUnique({ where: { email } });
    if (!user || !user.password || !(await bcrypt.compare(password, user.password))) {
      await prisma.authLog.create({
        data: { email, ip: req.ip || 'unknown', success: false },
      });
      res.status(401).json({ error: 'Невірний email або пароль' });
      return;
    }
    const payload = { userId: user.id, email: user.email, role: user.role };
    const accessToken = generateAccessToken(payload);
    const refreshToken = generateRefreshToken(payload);
    await prisma.refreshToken.create({
      data: {
        token: refreshToken,
        user_id: user.id,
        expires_at: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),
      },
    });
    await prisma.authLog.create({
      data: { user_id: user.id, email, ip: req.ip || 'unknown', success: true },
    });
    res.cookie('refreshToken', refreshToken, {
      httpOnly: true,
      secure: true,
      sameSite: 'none',
      maxAge: 7 * 24 * 60 * 60 * 1000,
    });
    res.json({
      accessToken,
      user: { id: user.id, email: user.email, full_name: user.full_name, role: user.role },
    });
  } catch {
    res.status(500).json({ error: 'Помилка сервера' });
  }
};
